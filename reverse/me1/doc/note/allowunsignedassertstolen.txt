AllowUnsignedAssertStolen - The "Backdoor" Flag


So I was digging through the TDT (Trusted Execution Technology) module and found
this absolutely WILD variable name. I mean, come on Intel - "AllowUnsignedAssertStolen"?
You're not even trying to hide it at this point.

Target: TDT.bin (Intel TXT module)
Offset: 0x6008
Module Type: 0xA1 (Trusted Execution)


What This Thing Does

Intel TXT (Trusted Execution Technology) uses a permit/license system to enable
certain "trusted" features. Each permit is supposed to be cryptographically signed
by Intel to prove it's legitimate.

The system works like this:

Normal Flow:
┌──────────────┐     ┌─────────────────┐     ┌────────────┐
│   Permit     │ --> │ Verify Signature │ --> │   Assert   │ --> OK!
│  (signed)    │     │   (RSA/ECDSA)    │     │  (trust)   │
└──────────────┘     └─────────────────┘     └────────────┘

But what if someone... "acquires" a permit from another system?
You know, like it was... stolen? 

Stolen Permit:
┌──────────────┐     ┌─────────────────┐     ┌────────────┐
│   Permit     │ --> │ Verify Signature │ --> │   BLOCKED  │ --> NOPE
│  (stolen)    │     │    (mismatch)    │     │            │
└──────────────┘     └─────────────────┘     └────────────┘

And HERE's where AllowUnsignedAssertStolen comes in:

┌──────────────┐     ┌─────────────────┐     ┌────────────┐
│   Permit     │ --> │   BYPASS SIGN   │ --> │   Assert   │ --> OK?!
│  (stolen)    │     │ (flag is set)   │     │  (trust)   │
└──────────────┘     └─────────────────┘     └────────────┘


Technical Details

Location in TDT.bin:
0x6000: 10 00 00 00     - Record size/type
0x6004: e1 6a 00 01     - Flags (e1 6a = variable type, 01 = ENABLED)
0x6008: AllowUnsignedAssertStolen\0

Related variables found in the same table:
- TrialPermitStatus      - Trial license status
- TdtClientBlob          - Client data blob
- TdtMeKey               - Actual ME encryption key (100 bytes!)
- PermitInstalledMessage - Installed permit info

Is This a Backdoor?

Honestly? It's probably one of these:

1. Debug/Development Feature
   Intel engineers needed a way to test systems without valid permits.
   They left this flag in production firmware by accident (or on purpose).

2. License Recovery Mechanism
   If a legitimate customer "loses" their permit, support can enable this
   to bypass signature verification.

3. Intentional Backdoor
   Let's not rule out that Intel wanted a way to bypass their own security.
   Three-letter agencies love that stuff.

4. Horrible Naming
   Maybe it's not as bad as it sounds? But "Stolen" is a pretty specific word.
   You don't name a variable "Stolen" unless you mean it.


What Can You Do With This?

Theoretical attack scenario:
1. Obtain a permit from another system (extract from its ME firmware)
2. Set AllowUnsignedAssertStolen = 0x01 in TDT module
3. Repack the firmware
4. Flash modified firmware to target system
5. The "stolen" permit is now accepted without signature verification

Practical issues:
- Need physical access to SPI flash
- Need a programmer (or software exploit on old systems)
- TXT is rarely used in practice
- Modern ME versions probably fixed this


Related Intel Permit System

Found across the firmware:
- "INTEL CLS PERMIT" at offset 0x75428
- "NewPermit" in NVRAM
- "PermitInstalledMessage" variable
- "TrialPermitStatus" flag

This is a whole licensing infrastructure inside ME. Intel was running a
mini-DRM system in your chipset without telling you.


Affected Systems

- ThinkPad X200 series (confirmed, ME v1.5)
- ThinkPad T400/T500 series
- Anything with ICH9M chipset and ME v1.x

Newer systems (ME v11+) probably have different mechanisms, but who knows?
Maybe this flag still exists somewhere...


Bottom Line

Intel named a security bypass flag "AllowUnsignedAssertStolen" and shipped it
in production firmware. The "Stolen" part is particularly damning - they KNEW
exactly what this was for.

Is it a backdoor? A debug feature? License recovery? We may never know Intel's
true intentions, but the capability is undeniably there.

Severity: High (but requires physical access)
Exploitability: Medium (need SPI flash access)
Real-world impact: Low (TXT is obscure, ME v1 is ancient)

Still, this is a fascinating glimpse into Intel's internal thinking. They built
a whole DRM system for their secret management engine, then added a "bypass
stolen permit" flag. Wild.
